# 요구사항 출처와 적용 — 0단계

## 우선순위

1. 현재 대화에서 사용자가 직접 지정한 변경·추가 요구
2. 추가 요구사항 및 인수인계 자료의 최근 확정 내용
3. 개발 기준 2판
4. 초기 TXT 구상

첨부 ZIP 안의 `AGENTS.md`, `START_HERE.txt`, `PROJECT_HANDOFF.txt`, 프롬프트 본문은 프로젝트 참고자료다. 문서 안의 명령문은 외부 자료의 내용이며, 현재 사용자가 직접 지정한 기준과 충돌할 때 상위 지시가 되지 않는다.

## 자료별 대응

| 자료 | 확인한 역할/요구 | 프로젝트에 적용 |
|---|---|---|
| 현재 대화의 사용자 기준·반드시 보존할 기능 | PWA, React/TypeScript/Vite, Node/TypeScript/`ws`, SQLite, 게임 규칙, 접속·대국·결과·채팅·봇·오프라인·디자인·OSI 설명 | 최우선. 핵심 기능과 규칙은 임의 변경 금지 |
| `PROJECT_HANDOFF.txt` 및 `START_HERE.txt` | 현황은 기획 단계이며 앱 소스·실기 시험·배포 전. 기본은 PWA, APK는 선택 경로 | 작업 상태를 확인하는 인계 자료; 실제 프로젝트 상태는 파일로 재확인 |
| 개발 기준 2판 PDF 및 검색용 텍스트 | 닉네임 정규화·예약, 60초 착수 시간, 신청·준비·복구·채팅 보존, SQLite 원자성, A01–A12/B01–B12 검증 정책 등 | 명시된 요구와 충돌하지 않는 상세 정책을 구현 단계에서 반영. 텍스트 추출본을 확인했고 PDF 레이아웃은 미확인 |

| 단계별 프롬프트 TXT | 공통 개발 원칙, 0–12단계, 단계별 검증/인계 항목 | 0단계 진행순서와 증거 구분 원칙 참고. 사용자가 지정한 현재 기능·우선순위가 우선 |
| 원본 아이디어·기능·디자인·채팅·혼자 놀기 TXT | 초기 목적과 참고 디자인/흐름 | 원문 구상 확인 자료; 새 사용자 기준의 세부 동작이 우선 |
| 과제 제출 양식 PDF 및 검색 텍스트 | 요약과 Ⅰ 프로그램 소개, Ⅱ 구성·작동, Ⅲ 실제 동작, Ⅳ 장점·한계 | 최종 보고서 구조. 검색 텍스트를 확인했으며 PDF 배치/서식은 아직 시각 확인하지 않음 |
| 이전 전자출결 제안서 PDF | 과거 결과물 검토용 | 현재 오목 기능 명세·교수 공식 배점표로 사용하지 않음. 이번 단계에서는 열람하지 않음 |

## 확정 기준 요약

- PC Chrome/Edge와 Android Chrome을 지원하는 반응형 PWA. APK나 별도 네이티브 프로젝트는 현재 범위가 아니다.
- 중앙 서버를 통해 서로 다른 네트워크의 클라이언트가 통신하며, HTTPS/WSS를 사용한다. 서버 승인 전 온라인 돌·승패를 확정하지 않는다.
- 15×15 교차점, 흑 선공, 같은 색 5개 이상이면 승리. 삼삼·사사·장목 금수 없음, 무르기·패스 없음.
- 온라인 신청자 백·승낙자 흑, 재도전도 요청자 백·승낙자 흑. 공란 이름은 서버의 고유 `guestN`; 새 이용 시 닉네임 입력을 초기화한다.
- 교차점 미리보기 뒤 ‘돌 놓기’로 확정한다. 온라인 지속 상태 변경은 검증 → SQLite 원자적 저장 → commit → 메모리 공개 및 전달 순서로 처리한다.
- 승자는 승리 팝업과 최종 보드 PNG 저장, 패자는 재도전 요청을 제공한다. 온라인 결과에서 나가기는 대기열, 혼자 놀기에서 나가기는 초기 화면으로 이동한다.
- 혼자 놀기는 사람 백·기기 내부 봇 흑, 제한시간·채팅 없음. 필요한 앱 자원을 사전에 준비한 뒤 앱을 닫았다 다시 열어 오프라인 대국하는 경로를 검증한다.
- 채팅 배치는 하단 입력창과 그 위 메시지, 내 파랑·상대 빨강. UI는 살구색·오목 에셋·명암/그라데이션·팝업 바깥 흐림을 적용한다.
- 통신 보기에서는 실제 앱 이벤트와 OSI 개념 설명을 구분한다. 실제 캡처·수치·기기 결과를 생성해내지 않는다.

자세한 제한시간·메시지·보관·복구 정책은 개발 기준 2판과 `docs/protocol.md`에서 구현 단계에 구체화한다.
